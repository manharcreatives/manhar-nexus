SSE moved into `openEventStream`: own reconnect with exponential backoff (1 s .. 30 s, +-30 % jitter, reset after a successful open), immediate reopen on `bye {refresh}`, backoff after `token-changed`/`unavailable`, browser-managed retries left alone. Every stream hint re-reads `/state` (or the menu for `menu.changed`/`table.updated`/`bye`). 404 or 403 `MENU_DISABLED` (also arriving mid-session) flips the page to its error state, clears caches and stops polling for a rotated QR. Polling underneath: 45 s state / 2 min menu while the stream is up, 10 s / 30 s while it is down, **10 s while one of our orders waits for the waiter** (see 4.1). ## 3. Real integration (scratch setup, nothing of it in the repo)

Setup: embedded PostgreSQL 17 (`$HOME/qweb-int/pgdata`, port 15437), scratch API copy `$HOME/qweb-api` (Prisma client-engine hacks per 07/11 reports), demo seed (13 QR codes, 11 pictures), the API built with `tsc`, the production web build served by a small Caddy-like proxy that strips `/api` and sets `X-Forwarded-Prefix: /api` (so picture URLs are absolute `http://host/api/media/...` exactly as in production). Staff actions were done through the real staff API (owner/waiter/kitchen demo users). Browser: Chromium 148 under `playwright-core` (the Playwright CDN is blocked on the VM; the npm package `@sparticuz/chromium` ships a binary), mobile viewport 390x844, DPR 2. Scripts: `$HOME/qweb-int/{staff,capture}.mjs`, `$HOME/qwtools/e2e-{a,a2,b1,b2}.mjs`. Each device call is capped, so a run is split in four.

**e2e-a + e2e-a2: 32 + 18 checks, all pass.** Menu renders with the cover, all 6 dish photos loaded (`/media` absolute URLs), 3D ring (perspective 1150 px, preserve-3d), cards tilt in perspective, hero parallax follows scroll, hero collapses into the compact bar, rail highlights the section in view; add to cart (quick add + variant sheet), dock + estimate, cart says the waiter confirms first; submit sends `Idempotency-Key` + `X-Guest-Token` and no prices; staff inbox receives it (id == service request id); staff edit -> "Adjusted by your waiter"; confirm -> Confirmed, accept -> Preparing, prepare+ready -> Ready, serve -> Served, each **live over SSE in 0.5-0.6 s**; timeline lists real statuses; rejection shows "Your waiter could not accept this order" + the reason (0.14 s); another guest's confirmed order is shown as a table order; waiter call is seen by staff and the banner clears on acknowledge (0.5 s); bill RUNNING with CGST + SGST and no UPI button; "Request bill" reaches staff as a bill call; after staff invoice + finalise the bill turns FINAL and "Pay by UPI" appears live (0.5 s), total equals the invoice, invoice reference shown; pay sheet renders the QR and the deep link `upi://pay?pa=...&am=<exact due>`; after staff records cash the sheet says "Payment confirmed" (0.65 s); no console/page errors, no staff endpoint ever called from the guest page, no spurious offline banner.

**e2e-b1: 19/19.** Lost response: the first POST reaches the server, the response is dropped -> "order is saved" message, cart kept, server already holds exactly one order, the retry reuses the same Idempotency-Key and the server still holds exactly one order. `?mock=1&mode=auto` on the production build shows the real restaurant and never requests the mock chunk. Closed table: "not open yet" banner, menu browsable, no Add buttons, no guest session requested; when staff open the table the page unlocks by itself (0.5 s). Rotating the QR flips an open page to "This QR code is no longer active" (1.0 s) and a fresh load of the old link shows the same (cache dropped). Disabling the table flips an open page to "digital menu is switched off" (0.7 s). A dish sold out while in the cart leaves the cart live (2 s) and the card is marked sold out.

**e2e-b2: 5/5.** Stream blocked for the first two attempts: third attempt goes through after the backoff, and a confirm then arrives live (0.2-0.6 s). Stream permanently blocked: the polling fallback delivers the status change (5.3 s, poll interval 10 s). Offline banner appears with the network off and clears when it is back.

## 4. Backend observations (for the API owner; not changed here)

1. **Waiter edit before confirmation emits no event.** `GuestHub.snapshot` signs an order as `status:editCount`; a pre-confirmation edit (`OrderEditService`, draft) changes lines and total but neither, so no `order.updated` is sent. Measured: the guest only saw "Adjusted by your waiter" after 4-8 s, i.e. through the page's own 10 s polling (added for exactly this). Suggestion: include the guest-visible total (or a line-hash) in the per-order signature.
2. **Waiter call opening emits no event; only closing does.** `diff()` sends `waiter.ack` when `before.waiterOpen && !after.waiterOpen`. The guest who calls the waiter refetches `/state` itself so they see it; a second device at the same table would only learn about the open call on its next poll. Suggestion: also emit `waiter.ack {}`/a new `waiter.called {}` on open (hints only).
3. Minor: `thumbUrl` is the same URL as `imageUrl` for the demo pictures (seed sets both), so `srcset` there offers identical files; harmless. Rejected orders report `totalMinor: 0` (cancelled lines excluded); the page hides the total for them.
4. Demo data has no `signature`/`chef` tags on 3+ photographed dishes, so the 3D signature ring does not appear for the stock demo seed (the page only builds it from 3+ tagged photographed dishes, deliberately, to avoid claiming "signature" falsely). In the browser run 4 dishes were tagged through `PATCH /admin/menu/items/:id/presentation`. The staff catalog editor still cannot set tags.

## 5. Not verified / known limits

- Screenshots with an open sheet or the 3D ring time out under software rendering on this VM, so the visual check was limited to the hero, the dish cards and the FINAL bill sheet (looked right, dark tokens intact); the ring, cart and pay sheet were verified by DOM/computed-style assertions, not by eye. Real-device 60 fps on a mid Android phone was not measured.
- `sharp` path (480 px thumbs, WebP, blur data URI, colour) is not installed on the VM, so `blurDataUri`/`color`/real `thumbUrl` rendering was only unit-tested and type-checked, not seen in a browser.
- `UPI_UNAVAILABLE` and `BILL_NOT_READY` copy: `BILL_NOT_READY` was recorded; `UPI_UNAVAILABLE` is the documented envelope (UPI was already enabled in the scratch DB when the recording ran). Apple Safari / Firefox EventSource behaviour not tested (Chromium only).
- A guest token that expires (12 h) *after* a response was lost could, in theory, create a second order on the re-issued token (the idempotency key is namespaced per guest token). Not reproducible in practice (tokens end with the visit) and left as is.
- The caps (25/20/60) are mirrored as constants; if an operator changes `GUESTMENU_MAX_*` the server answers 400 and the page shows the server message after a menu refresh.
