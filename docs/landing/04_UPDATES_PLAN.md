## A. Software updates requested
1. **Multiple roles at once in one browser.** Today one Chrome profile = one login (shared session), so owner/cashier/waiter/kitchen cannot be open in separate tabs/windows simultaneously. Make sessions per-tab/per-window (or per explicit "profile slot") so different users can be signed in at the same time in the same browser, WITHOUT weakening security (ADR-023/024 token strategy: study them; write a new ADR-034 for the change). Consider: access token in memory, refresh token per tab in sessionStorage (or a named session slot), refresh-cookie path/rotation conflicts between tabs, logout of one tab must not log out others, session-hint logic, realtime/SSE per tab, 'remember me on this device' for single-user devices. Keep existing tests green and add tests.
2. **Order edit before kitchen starts.** If the kitchen has not started the order (status before PREPARING / not yet acknowledged — determine exact state from code/spec), staff must be able to edit it (add/remove/change quantity, variants/add-ons, notes) with an audit-trailed edit (append-only; no silent mutation of financial/audit history; idempotent; concurrency-safe — see ADR-016/017). After the kitchen starts: editing blocked with a clear explanation (cancellation/void rules stay as is). The kitchen screen must reflect edits live (SSE) and flag "edited" visibly.
3. **Order taking UI: "Added" vs "Menu" must never mix.** In the order builder (waiter taking an order) show clearly separated zones: (a) the running order (items already added, with qty steppers, remove, notes, running total, sticky and visually distinct) and (b) the menu to pick from (categories, search, big tap targets, sold-out marked). Added items must be unmistakable in the menu too (badge with qty) but live in their own panel; on phones use a bottom-sheet/segmented 'Menu | Order (3)' pattern, on desktop a two-column layout. Optimised for speed and zero confusion under pressure. Keep the dark theme + design system (ADR-031).
4. **Kitchen card timeline.** Kitchen display cards currently show an elapsed time from order start. Keep a small elapsed-time label, but make it clickable: opens a small popover/card showing the order's TIMELINE — every action with timestamp and actor and the duration between steps (placed → edited → accepted → preparing → ready → served …). Source: existing status events / audit trail; add an API endpoint only if needed.
5. **Checkout: change payment method / go back.** In checkout the cashier/waiter may pick Cash and then learn it must be UPI (or vice versa): provide Back / change-method without losing entered data and without duplicate payments (idempotency), until payment is actually recorded. Also handle partial mistakes safely (e.g. UPI UTR entered then switched).
6. **Dialog/card closes when a text selection drag ends outside.** Selecting text inside a card/dialog and releasing the mouse outside closes it — wrong. Fix the shared overlay/dialog logic (backdrop must close only when BOTH mousedown and mouseup/click started on the backdrop) everywhere in apps/web (ui/Dialog.tsx, drawers, popovers, command palette etc.); add tests.
7. **Waiter can show the BILL and the payment QR.** Cashier generates the bill; the WAITER goes to the table to collect payment. Give the waiter (permission-gated, add permissions if needed + role defaults) a customer-facing "Show bill" view (clean, large, itemised, GST lines, total, restaurant name) and a "Show payment QR" view (UPI QR built from the restaurant's UPI id/VPA + exact payable amount + bill reference, via `qrcode` library, big and high-contrast, with a UPI deep-link button for the customer's phone and a clear 'Waiting for payment' → staff records/ confirms payment as the checkout flow already does). Needs a restaurant setting for UPI VPA/payee name (check existing manual UPI provider config).

### QR menu API contract (Q-API agent implements; Q-WEB + Q-STAFF consume; amend this section if reality differs and tell the others in your report — keep it current)
Public (no auth, rate-limited, prefix as existing API prefix; web calls `${API_BASE}/public/menu/...`):
- `GET  /public/menu/:tableToken` -> 200 { business:{name,slug,tagline?,logoUrl?,coverUrl?,accentColor,currency:'INR'}, table:{label,areaName?,open:boolean}, settings:{ordering:'off'|'confirm'|'auto', callWaiter:boolean, payment:{upi:boolean}}, categories:[{id,name,description?,imageUrl?}], items:[{id,categoryId,name,description?,priceMinor,imageUrl?,blurDataUri?,veg?:'veg'|'nonveg'|'egg',tags:string[],spice?:0-3,soldOut:boolean,variants:[{id,name,priceMinor}],addOnGroups:[{id,name,min,max,options:[{id,name,priceMinor}]}]}], etag, serverTime }  (supports If-None-Match -> 304)
- `GET  /public/menu/:tableToken/stream` (SSE) events: menu.changed {etag}, table.updated {open}, order.updated {orderId,status,...}, bill.updated {...}, waiter.ack
- `POST /public/menu/:tableToken/guest` -> {guestToken, expiresAt} (device guest identity; optional {displayName})
- `POST /public/menu/:tableToken/orders` (header X-Guest-Token, Idempotency-Key) { lines:[{itemId,variantId?,addOnOptionIds?:string[],qty,note?}], note? } -> 201 { orderId, status:'AWAITING_CONFIRMATION'|'CONFIRMED', totalMinor }
- `GET  /public/menu/:tableToken/state` (X-Guest-Token) -> { orders:[{id,status,lines,placedAt,timeline:[...]}], bill:{subtotalMinor,taxLines:[...],totalMinor,paidMinor,dueMinor,status}, waiterCall:{open:boolean} }
- `POST /public/menu/:tableToken/waiter` { reason:'call'|'bill'|'water'|'other' } -> 202 ;  `POST /public/menu/:tableToken/pay-intent` { method:'upi' } -> { upiUri, qrPayload, amountMinor, reference } (staff still confirm receipt)
Staff (existing auth/permissions; new permissions `restaurant.qr.manage`, `restaurant.guestorder.manage`): `GET/POST/PATCH /admin/qr/tables` (list tokens, rotate, enable), `GET/PATCH /admin/qr/settings`, `POST /admin/menu/items/:id/image` (+DELETE), `GET /admin/guest-orders?status=` , `POST /admin/guest-orders/:id/confirm|reject|edit`.
Money = integer minor units (paise). Terminology per CANONICAL_GLOSSARY (Service Request = the order; Guest Session; Checkout; KOS). Guest orders are Service Requests with source=GUEST.
